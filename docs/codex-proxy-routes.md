# Codex tool routes behind a reverse proxy

When Codex connects to CLIProxyAPI through another reverse proxy or local
bridge, successful text responses do not establish that image generation,
image editing, and standalone web search can reach CLIProxyAPI. These tools
use separate HTTP routes. A bridge that only forwards Responses and model
listing can reject tool requests before CLIProxyAPI receives them.

For initial client configuration, follow the [Codex setup guide](https://help.router-for.me/agent-client/codex).
This note covers an additional proxy in front of CLIProxyAPI with a client
base URL ending in `/v1`.

## Routes to forward

Allow the following method/path pairs for these Codex features. They are
registered in [internal/api/server_routes.go](../internal/api/server_routes.go).

| Feature | Method | Path |
| --- | --- | --- |
| Model listing | GET | `/v1/models` |
| Text responses | POST | `/v1/responses` |
| Responses WebSocket transport | GET with WebSocket upgrade | `/v1/responses` |
| Context compaction | POST | `/v1/responses/compact` |
| Image generation | POST | `/v1/images/generations` |
| Image editing | POST | `/v1/images/edits` |
| Standalone web search | POST | `/v1/alpha/search` |

Match methods and paths explicitly in a restrictive bridge. Adding the three
tool routes does not require exposing management endpoints or accepting all
paths under `/v1`.

Preserve JSON request bodies and multipart image uploads, including their
`Content-Type` boundary. Forward response status codes and content types,
stream Responses without buffering, and support WebSocket upgrades when
enabled by the client. Continue authenticating requests at the bridge and
supply the credential expected by CLIProxyAPI; routing changes do not require
disabling authentication or browser-origin restrictions.

The `/v1/alpha/search` handler forwards the Codex search payload; it is not a
chat-completions request. Do not translate it into a prompt or rewrite it to
`/v1/responses` in the outer proxy.

## Diagnosing tool failures

1. Record the failing method, path, HTTP status, and error message. Do not log
   authorization headers, cookies, uploaded images, or request bodies.
2. Check whether the outer proxy forwarded the request. An error generated by
   that proxy, together with no matching request at CLIProxyAPI, points to its
   route configuration. Confirm that request logging is enabled before relying
   on the absence of a log entry.
3. If CLIProxyAPI receives the request, check its configuration and the returned
   upstream error. In particular, `disable-image-generation: true` intentionally
   returns 404 for both Image API routes. Standalone search needs an eligible
   Codex credential; API-key credentials require the `alpha-search` opt-in and a
   compatible `base-url`, as described in [config.example.yaml](../config.example.yaml).
4. Reload the changed proxy and verify image generation and standalone search
   independently. A successful text response or model-list request does not
   exercise either route.

The Image API handlers are implemented in
[openai_images_handlers.go](../sdk/api/handlers/openai/openai_images_handlers.go).
Correct a missing outer-proxy route in that proxy's configuration. CLIProxyAPI's
existing handlers and the user's authentication setup do not need to change.
