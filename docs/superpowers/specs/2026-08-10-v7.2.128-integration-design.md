# v7.2.128 Integration Design

## Context and Problem

The current feature branch, codex/fix-responses-item-id, descends from v7.2.119 and contains the reviewed HTTP Responses input-item ID normalization fix. At the documented starting point, its source tip is 12f88ee5c06bd801c970ae051d6ce3368dbf4eb6.

The upstream remote is https://github.com/router-for-me/CLIProxyAPI.git. Its v7.2.128 tag resolves to bd34ceca04209ef0460f4b05e3a1a047fb7fad2a. The origin fork does not advertise that tag, so future integration must obtain the exact tag from upstream rather than assume it is available through origin.

This document specifies the future upstream integration and the contract that the existing fix must retain. Creating this document does not fetch, merge, rebase, cherry-pick, build, deploy, or restart anything.

## Goals and Non-goals

Goals:

- Integrate exactly upstream v7.2.128 while preserving the reviewed feature-branch history.
- Retain handler-boundary normalization for HTTP POST /v1/responses.
- Preserve upstream v7.2.128 behavior except where the approved normalization necessarily overlaps it.
- Verify both the focused normalization behavior and the merged branch against a clean v7.2.128 baseline.

Non-goals:

- Do not replace the handler fix with executor-only sanitization.
- Do not broaden normalization to websocket, compact, translator, or tool-pairing paths.
- Do not alter call_id values, input order, valid IDs, unknown item types, or unrelated fields.
- Do not refactor unrelated code, rewrite history, or duplicate the feature on another branch.
- Do not build a production image, deploy, or restart cliproxyapi-cli without separate approval.

## Upstream Partial-Fix Evidence

Systematic analysis in a disposable clone classifies upstream v7.2.128 as PARTIALLY_FIXED.

| Observation | Evidence | Result |
| --- | --- | --- |
| HTTP handler boundary | OpenAIResponsesAPIHandler.Responses forwards item_call123 and item_msg456 unchanged to its execution boundary. | The upstream handler does not establish normalization at the HTTP boundary. |
| Late Codex sanitization | SanitizeCodexInputItemIDs, introduced around commit 5e25566, runs in the Codex executor immediately before the real Codex HTTP POST. | It changes the IDs to fc_item_call123 and msg_item_msg456 by prepending a valid prefix to the complete original invalid ID. |
| Temporary handler capture | A real-handler capture probe returned HTTP 200 and observed exactly one execution payload that still contained item-prefixed IDs. | The handler behavior above is directly observed, not inferred. |
| Temporary real-upstream probe | A handler-to-real-Codex-upstream probe observed fc_item-prefixed and msg_item-prefixed IDs in the final upstream request and succeeded format-wise. | The late sanitizer prevents the observed Codex upstream format rejection. |

The upstream sanitizer is useful protection for Codex execution, but it does not guarantee handler-boundary behavior or cover non-Codex execution paths, including plugin paths.

## Considered Approaches

| Approach | Decision | Rationale |
| --- | --- | --- |
| Keep the handler fix and merge the exact upstream tag | Selected | Provides handler-level and Codex-executor protection, preserves reviewed history, avoids double normalization, and produces an auditable integration point. |
| Remove the current patch and rely only on the late upstream sanitizer | Rejected | Minimizes local delta but loses the handler and non-Codex guarantee and changes the approved ID semantics. |
| Make the handler reuse the executor sanitizer | Rejected | Couples the OpenAI SDK handler to executor-specific behavior and adopts fc_item and msg_item semantics instead of the approved replacement semantics. |
| Rebase the feature branch onto v7.2.128 | Rejected | Rewrites reviewed feature commits and removes the explicit upstream integration point. |
| Create a new branch and cherry-pick the fix | Rejected | Duplicates reviewed work without a benefit over merging the tag into the existing feature branch. |

## Selected Git Architecture and Provenance

Future implementation will fetch the exact v7.2.128 tag from upstream, confirm that it resolves to bd34ceca04209ef0460f4b05e3a1a047fb7fad2a, and merge it into codex/fix-responses-item-id with an explicit non-fast-forward merge commit.

~~~sh
git fetch upstream refs/tags/v7.2.128:refs/tags/v7.2.128
test "$(git rev-parse v7.2.128^{commit})" = bd34ceca04209ef0460f4b05e3a1a047fb7fad2a
git merge --no-ff v7.2.128
~~~

The merge preserves the current reviewed commits rather than rebasing or rewriting them. Its first parent must be the feature-branch tip immediately before the merge, which descends from 12f88ee5c06bd801c970ae051d6ce3368dbf4eb6. Its second parent must be bd34ceca04209ef0460f4b05e3a1a047fb7fad2a. This directly records the upstream integration provenance.

## Conflict Rules and Preservation Contract

No conflict is expected in the normalization helper or its test. The probable overlap is sdk/api/handlers/openai/openai_responses_handlers.go: upstream v7.2.128 changes imports and stream-error handling, while the feature branch adds one request-body call near processing. Resolve only actual overlaps and retain both upstream behavior and the handler normalization. Do not refactor adjacent code.

The following three paths define the existing feature that must survive the merge:

- sdk/api/handlers/openai/openai_responses_handlers.go
- sdk/api/handlers/openai/openai_responses_input_item_ids.go
- sdk/api/handlers/openai/openai_responses_input_item_ids_test.go

For HTTP POST /v1/responses only, after the request body is read and before prepareCodexMultiAgentV2Tools and the streaming or non-streaming split:

| Input item | Required output |
| --- | --- |
| function_call with id item_<non-empty suffix> | id fc_<same suffix> |
| message with id item_<non-empty suffix> | id msg_<same suffix> |

The normalization preserves the suffix, call_id, item order, already-valid IDs, unknown item types, and every other field. It does not change websocket, compact, translator, or tool-pairing processing. The upstream sanitizer is idempotent for already-valid fc_ and msg_ IDs, so the selected handler result remains fc_call123 and msg_msg456 without a second prefix.

If a conflict is architectural, affects an unlisted behavior, or cannot preserve this contract together with upstream behavior, stop rather than invent a broader resolution.

## Verification and Success Criteria

After the future merge, all of the following are required:

1. Record the merge commit SHA immediately after the merge. Confirm the fetched tag resolves to bd34ceca04209ef0460f4b05e3a1a047fb7fad2a, then prove it is an ancestor of final HEAD with git merge-base --is-ancestor bd34ceca04209ef0460f4b05e3a1a047fb7fad2a HEAD. Inspect git rev-list --parents -n 1 <merge-commit-SHA> to confirm that explicit merge has the pre-merge feature tip and the exact upstream tag commit as parents.
2. Review the three listed handler, helper, and test paths to confirm the preservation contract survives. Run the direct and HTTP-boundary regressions:

~~~sh
go test ./sdk/api/handlers/openai -run '^(TestNormalizeResponsesInputItemIDsRewritesObservedLocalIDs|TestNormalizeResponsesInputItemIDsPreservesValidAndUnknownItems|TestResponsesNormalizesLocalInputItemIDsBeforeExecution)$'
~~~

The capture assertion must observe fc_call123, msg_msg456, and the unchanged call_id value.
3. Run the complete OpenAI handler package:

~~~sh
go test ./sdk/api/handlers/openai
~~~

4. Establish a clean v7.2.128 baseline in a separate disposable worktree or clone, using the same Go version and test environment as the merged branch. Run the complete suite in that clean baseline and in the final merged branch:

~~~sh
go test ./...
~~~

Record the exact failing tests and failure causes in the clean v7.2.128 baseline. A final failure is baseline-only only when the same test has the same documented cause in that clean run. The merged branch must introduce no additional failures. Do not assume that the three failures recorded for v7.2.119 remain the v7.2.128 baseline.
5. Refresh the code-review graph from final HEAD, run its change-detection and impact review, and audit the merge scope. The reviewed result must be upstream v7.2.128 plus the three preserved normalization paths, without unrelated local refactoring.
6. Run fresh specification and code-quality reviews against the final merge result. Finish only with a clean git status, a clean git diff --check result, and no unreviewed changes.

## Error and Rollback Handling

Before the merge commit exists, stop for unresolved or unexpected conflicts, additional regressions, or a failure of the preservation contract. If a merge is in progress and must be abandoned before it is committed, git merge --abort is allowed.

Never use a destructive reset. After a merge commit, correct forward with a new auditable commit rather than rewriting history. Preserve the user-owned main-checkout .gitignore state; this integration must not modify, discard, or reset it.

## Deployment Boundary

Deployment is explicitly outside this integration design. No production image build and no cliproxyapi-cli restart are authorized without separate approval.
