# 上游 v7.2.133 干净合并设计

## 目标

将上游 CLIProxyAPI `v7.2.133` 合并到当前二开 Fork，同时保留现有的请求日志录制、格式归一化、压缩、TOS 上传、Supabase 上报和日志大小统计行为。

## 范围

- 以当前 Fork 的 `main` 分支为起点。
- 直接合并已经获取的上游 `v7.2.133` 标签。
- 不复用实验性分支 `codex/upgrade-v7.2.132-auth-log-hardening` 中的提交。
- 保留 Fork 独有的日志上传、日志 QA、仪表盘集成、部署和配置行为；只有在上游接口发生变化时才进行必要适配。
- 在不移除 Fork 功能的前提下，采用上游的核心重构和问题修复。

## 冲突处理策略

合并预演发现以下 5 个文件存在文本冲突：

1. `.gitignore`：保留 Fork 特有的本地忽略项，同时加入上游新增的忽略项。
2. `docker-compose.yml`：保留日志 uploader、日志 QA、日志与插件持久化目录以及 Fork 环境变量，同时采用兼容的上游部署改动。
3. `go.mod`：保留 TOS SDK 和 Fork 依赖，同时采用上游依赖升级；使用 Go 工具重新生成 `go.sum`。
4. `internal/api/server.go`：采用上游的 Server 拆分与重构，并在新的 Server 结构中重新接入 Fork 的中间件、管理页面资源、Home 集成、请求日志、日志 QA 和使用量接口。
5. `internal/logging/request_logger.go`：采用上游拆分后的请求日志架构，将 Fork 行为迁移到对应的职责文件中，但不引入尚未完成的 auth-hardening 实验行为。

对于双方都曾独立修改、但 Git 自动合并成功的文件，仍需检查是否存在语义冲突，尤其是配置字段和 API Key 管理逻辑。

## 必须保留的行为契约

- 成功请求继续在预期的按 Key 分类目录中生成完整的 `.log` 文件。
- 流式和非流式日志继续保留 `internal/loguploader` 所依赖的日志区段。
- 保持现有的 `api-key-names` 和 `api-keys-no-log` 行为不变。
- `log-uploader` 继续将记录归一化为 JSONL，使用 Zstandard 压缩，以幂等方式上传到 TOS，向 Supabase 上报使用量，并准确记录 `source_bytes`、`jsonl_bytes` 和 `compressed_bytes`。
- 保持现有 uploader 状态、审计记录、outbox 和 Supabase 历史同步格式兼容。
- Docker 部署继续保留 Fork 的全部服务和持久化数据挂载。

## 验证方式

1. 运行日志、中间件、uploader、日志 QA、管理接口和管理页面资源的专项测试。
2. 完成 Go 代码冲突处理后运行 `gofmt -w .`。
3. 运行 `go test ./...`。
4. 执行强制编译验证：`go build -o test-output ./cmd/server && rm test-output`。
5. 检查最终差异和合并提交，生成准确的冲突处理报告。

## 回滚方式

现有 `main` 分支和实验性的 v7.2.132 worktree 均保持不变。如果干净合并结果不合适，只需删除新建的 worktree/分支，或继续从未改动的 `main` 分支开展工作。
