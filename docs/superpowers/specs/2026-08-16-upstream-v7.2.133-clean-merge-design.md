# Upstream v7.2.133 Clean Merge Design

## Goal

Merge upstream CLIProxyAPI `v7.2.133` into the customized fork while preserving the existing request-log recording, normalization, compression, TOS upload, Supabase delivery, and log-size accounting behavior.

## Scope

- Start from the fork's current `main` branch.
- Merge the fetched upstream `v7.2.133` tag directly.
- Do not reuse the experimental `codex/upgrade-v7.2.132-auth-log-hardening` commits.
- Preserve all fork-only log uploader, log QA, dashboard integration, deployment, and configuration behavior unless an upstream interface change requires adaptation.
- Adopt upstream core refactors and bug fixes where they do not remove fork functionality.

## Conflict Strategy

The merge preview identifies five files with textual conflicts:

1. `.gitignore`: retain fork-specific local exclusions and add upstream exclusions.
2. `docker-compose.yml`: preserve uploader, log QA, persistent log/plugin volumes, and fork environment variables while adopting compatible upstream deployment changes.
3. `go.mod`: retain the TOS SDK and fork dependencies while adopting upstream dependency upgrades; regenerate `go.sum` with Go tooling.
4. `internal/api/server.go`: adopt the upstream server split/refactor and reconnect fork middleware, management assets, Home integration, request logging, log QA, and usage endpoints in the new server structure.
5. `internal/logging/request_logger.go`: adopt the upstream split request-logger architecture and port fork behavior into the appropriate focused files without importing the unfinished auth-hardening behavior.

Files changed independently on both sides but auto-merged will be reviewed for semantic conflicts, especially configuration fields and API-key management.

## Preservation Contracts

- Successful requests continue to create complete `.log` files under the expected per-key directory.
- Streaming and non-streaming logs retain the sections consumed by `internal/loguploader`.
- Existing `api-key-names` and `api-keys-no-log` behavior remains intact.
- `log-uploader` continues to normalize records to JSONL, compress with Zstandard, upload idempotently to TOS, deliver usage to Supabase, and record exact `source_bytes`, `jsonl_bytes`, and `compressed_bytes` values.
- Existing uploader state, audit, outbox, and historical Supabase synchronization formats remain compatible.
- Docker deployment retains all fork services and persistent data mounts.

## Verification

1. Run focused tests for logging, middleware, uploader, log QA, management handlers, and management assets.
2. Run `gofmt -w .` after Go conflict resolution.
3. Run `go test ./...`.
4. Run the required compile verification: `go build -o test-output ./cmd/server && rm test-output`.
5. Inspect the final diff and merge commit to produce an exact conflict-resolution report.

## Rollback

The existing `main` branch and experimental v7.2.132 worktree remain untouched. If the clean merge is unsuitable, delete only the new worktree/branch or continue from the unchanged `main` branch.
