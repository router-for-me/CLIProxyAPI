# LiteLLM exporter

Enable `observability.accounting-outbox.litellm` with a persistent outbox, base URL, version `1.103.0`, and receiver profile `ai-proxy-completed-v1`. Restart after changes. Inject the proxy-admin key through the environment variable named by `admin-key-env` from central deployment secrets. YAML and the test harness contain only the variable name. Use HTTPS outside a trusted local network. Redirects are refused. Connect to the verified receiver without a gateway that can replace an upstream acceptance response with a rejection.

Apply [completed-failures.patch](../test/litellm/completed-failures.patch) to LiteLLM v1.103.0, tag commit `c991f4b01f5799eb0b0cab0fb63988e15c3a8a9d`, using `patch -p1` from its source root. The patch preserves completed success payloads, carries failure status into spend metadata, and records marked completed failures through LiteLLM's own accounting callback. Stock failure replay rebuilds zero usage and does not invoke the database cost logger. The patch adds an admin-only capability route so the exporter verifies the actual installed version/profile before claiming events. It adds no database writes outside LiteLLM's existing writer and does not claim idempotency.

Create dedicated LiteLLM users and teams through `/user/new` and `/team/new`, then create a virtual key through `/key/generate` with those owners. Set `clients[ClientKeyID]` to that existing key's SHA-256 `key-hash`, `user-id`, and `team-id`. `ClientKeyID` is the local accounting hash, not a LiteLLM key hash. The proxy-admin transport credential is never used as the spend identity. Keep spend logs and spend updates enabled and configure PostgreSQL persistence on LiteLLM. Without existing identities, spend rows can appear while identity counters fail to persist. Do not reuse these identities for inference through LiteLLM during reconciliation.

Batches contain at most 64 completed records. Export requires complete normalized token usage and a fully priced USD estimate. Missing attribution, partial usage, and unknown prices remain local with a mapping status. Raw evidence, prompts, responses, credential material, and provider error text are omitted. Failure and interruption carry a fixed safe error description. The original event and price provenance remain in the outbox.

The worker has no network timeouts, including dial and TLS handshake deadlines. This follows the repository policy without adding an exception. Cancellation interrupts network requests during service shutdown. A stalled receiver occupies only the exporter worker, while ingestion continues through its independent bounded local queue. Retries use exponential backoff for rate limits and worker failures, capped at a minute. Auth and route rejections wait an hour per claimed event. A 422 rejects the record permanently. Transport failures, service errors, malformed responses, and per-record callback failures are ambiguous because callbacks can have partial side effects. Remote error bodies are not logged or persisted.

A 200 reports callback completion, not a PostgreSQL commit. Successful submissions therefore also remain ambiguous until reconciled. LiteLLM queues persistence and can swallow callback errors. Ordinary completion IDs deduplicate spend-log rows at insertion but do not deduplicate daily aggregates, identity spend updates, or budget counters. Never reset ambiguous records to retryable merely because a spend row is missing.

For safe recovery, pause export by disabling it and restarting, drain all receiver persistence workers, and obtain spend rows plus user/team/key spend and daily token/request aggregates through LiteLLM read APIs. Compare an isolated identity's counter deltas with its pre-export baseline, covering the same event set and time range. `LiteLLMExporter.Reconcile` accepts receipts up to the configured outbox event ceiling, requires exactly one matching row per event and matching identity/model/provider/status/tokens/cost, and checks every mapped identity's aggregate delta. A verified report acknowledges all receipts in one local transaction. It never sends requests to LiteLLM or replays events. If rows or counters disagree, preserve the ambiguous event and investigate the receiver using its supported APIs. There is no automatic absent-event recovery or counter repair. Permanent rejection remains available through the existing explicit `Outbox.Resolve` API when an operator chooses to retain the loss instead of risking duplicate charging.

The SDK exposes `Service.AccountingExporterStatus`. Status changes appear in structured accounting logs. Outbox backlog includes unreconciled submissions, so reconcile before reaching the storage ceiling. Disablement, unavailable secrets, unsupported capabilities, and receiver outages do not modify inference behavior.

## Verification

Run `go test ./sdk/cliproxy/usage ./internal/config ./sdk/cliproxy`, then install `test/litellm/requirements.txt` in an isolated Python environment and run `LITELLM_LOCAL_MODEL_COST_MAP=True python -m pytest -q test/litellm/test_contract.py`. The fixture is generated by the Go mapper and checked for drift. Python tests apply the receiver patch to the installed pinned package and execute its actual replay, spend-log construction, daily queues, and identity spend queues. Duplicate replay increments aggregates again. Go tests cover lost responses, restart quarantine, cancellation, per-record failures, and safe reconciliation.

No live deployment credentials were provided. PostgreSQL row persistence, unique-constraint duplicate behavior in a deployed database, persistence-worker flushes, dashboard read APIs/UI, and live identity/budget counters remain unverified. The contract tests stop at LiteLLM's repository/queue boundaries and assert its `skip_duplicates` insertion policy. A deployment check must confirm three unique events, 30 input tokens, 15 output tokens, USD 0.000370368 estimated spend, one success and two failures, and the corresponding user/team/key totals. Repeating one success must leave three spend rows but increase aggregate requests to four, input tokens to 40, output tokens to 20, and spend to USD 0.000493824. Perform that duplicate check only on disposable dedicated identities, then use a fresh identity for normal export and reconciliation. Dashboard gateway request metrics describe requests to LiteLLM itself and are not replayed inference counts. Use spend-derived daily aggregates for exported accounting.
