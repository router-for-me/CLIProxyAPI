# Accounting outbox

Enable `observability.accounting-outbox` and set `data-path` to a persistent volume directory. Configuration changes require a service restart. CLI and embedded `Service.Run` use the same lifecycle. Only one accounting owner may attach to the process-wide usage manager, and only one process may open a data path. Replicas need separate paths. The bbolt lock remains held until shutdown finishes, even if the caller's shutdown deadline expires.

Accounting takes a bounded serialized snapshot before entering the existing, unbounded legacy usage dispatcher. Its dedicated worker performs local transactions only. No LiteLLM client or network exporter is introduced here. Durable acceptance is the successful completion of the bbolt write transaction with fsync enabled. `Outbox.Insert` returns at that boundary. The inference path's enqueue returns earlier and is not a durable acknowledgement. A crash between upstream completion and commit can lose accounting, including events waiting in memory. Graceful shutdown detaches admission and drains the queue, but waits at most `shutdown-seconds`. A blocked filesystem operation retains ownership in the background. Killing the process can lose its uncommitted queue. Crash-window losses cannot be counted after the fact.

Defaults are 512 queued events, at most 64 KiB of serialized data per event, 256 MiB of database capacity, 100,000 stored events, 168 hours of terminal history, and a 5-second shutdown wait. Oversized fields are rejected before serialization. Ingress memory is at most 32 MiB of serialized queue data plus one worker event and transient snapshots from concurrent publishers. Legacy usage plugins retain their existing memory behavior.

Admission reserves database space for copy-on-write transactions and freelist growth, so it can stop before the configured disk ceiling. Deleted pages are reusable, but bbolt does not shrink its file. At the high-water limit, conservative admission may require increasing capacity to permit further mutations. Pending events are never evicted to make room. Retention runs every 30 seconds in batches of 64 and deletes only acknowledged or permanently rejected deliveries and their raw events. The event-count ceiling bounds history even when retention lags. Event ID deduplication lasts as long as the event is retained. Replaying a deleted terminal event can insert it again.

Raw event bytes and delivery metadata occupy separate transactional buckets. New deliveries are pending. `Claim` changes pending or due retryable deliveries to ambiguous and increments their attempt number before any future external call. Only one worker can claim an event. `Resolve` requires that attempt number and records acknowledged, retryable, ambiguous, or permanently rejected outcomes. Retryable means the exporter knows the destination did not accept the event. Ambiguous deliveries survive restart and require explicit resolution. No automatic retry policy or exporter is included.

Storage errors drop the attempted insertion rather than blocking inference. Queue pressure and invalid or oversized events increment dropped-event counters. Startup corruption or an unavailable volume attaches a loss-counting sink and logs that accounting is unavailable for this run. Repair the volume and restart. A successful local commit preserves an event even if later delivery-state updates fail.

Existing logrus output reports backlog, oldest pending age, queue depth, persistence failures, and dropped events every 30 seconds for an open store. Persistence failure logs are rate-limited to the first failed insertion, with totals in periodic status. Shutdown logs the final counters. Embedded operators can call `Service.AccountingOutboxStats`, and local workers can call `Outbox.Stats`. Counters are process-lifetime diagnostics, while backlog and delivery states are durable. No UI or management endpoint is added.
